## 1. Autosave data loss — root-caused and fixed
Your Aleutian Spray edits were destroyed by a four-part design flaw (full write-up:
`docs/Autosave_Incident_2026-07-25.md`): a single autosave slot, written unconditionally every
1.5 s from whatever the session held — so reopening the pristine sample overwrote your draft
within seconds; and `hasUnsavedWork()` ignored wear records entirely, so the one existing
guard never fired for your wear marks. The edits are unrecoverable; the class of loss is gone.

**Built:**
- **Dirty gate** — autosave writes only when the session truly differs from the last
  saved/loaded state (full-snapshot comparison, wear + runout included). A freshly opened file
  can never clobber a draft again. Explicit save removes the session's draft entry.
- **Draft ring, last 3 unsaved sessions** (your request) — per-document identity; StartScreen
  now shows an "Unsaved drafts" list (name, age, tap to continue, X + confirm to discard).
  Old single-slot drafts migrate automatically.
- Files: `data/AutosaveManager.kt` (v2), new `data/DraftRing.kt` (pure ring + dirty-gate
  logic), `ShaftViewModel.kt`, `StartScreen.kt`, `AppNav.kt`.
- Tests: `DraftRingTest` (12), `AutosaveDraftSerializationTest` (3).

## ⚠ New finding for you (logged in TODO §2.3, not fixed — needs your on-device check)
While fixing #4 we found a real inconsistency: `ShaftRenderer` draws the taper trapezoid
strictly x-ordered (`startDiaMm` at the AFT face, unconditionally), while the Add-taper path
stores SET-first. Consequence: a FWD-end taper created via the Add dialog and **never edited
afterward** may *draw* with its small end against the body (inverted). Editing it in the
carousel re-stores x-ordered and fixes the drawing. Worth checking on-device; the durable fix
is picking one canonical storage order and normalizing on add/load — your call on when.
